# 性能与复现

## 1. 实测环境

| 项 | 值 |
|---|---|
| 服务端 | MariaDB 10.11.19（MySQL 兼容方言），本机 unix socket |
| 客户端 | `mysql` CLI，每次查询一个新进程（**含进程启动开销**） |
| Python | 3.11 |
| 机器 | 单机容器，未做 CPU/IO 隔离，缓存状态未严格控制 |
| 数据 | 合成日志，2021-07-01 ~ 2021-11-03，活动窗口 2021-07-07 ~ 2021-10-31 |

原始输出：[`verify-log.txt`](verify-log.txt)。

## 2. 三条路径对比（规则 r1）

同一份数据、同一条规则，分别跑：编译器自动选路（Tier 1）、强制递归后端（Tier 2）、
原始 `@用户变量` 解法。

| 用户数 | 日志行数 | 人日数 | Tier 1 | Tier 2 | `@变量`原版 | Tier1 vs Tier2 |
|---|---|---|---|---|---|---|
| 200 | 23,562 | 15,559 | **45.3 ms** | 75.2 ms | 93.8 ms | 1.7x |
| 1,000 | 117,817 | 77,955 | **205.2 ms** | 385.9 ms | 418.7 ms | 1.9x |
| 4,000 | 471,377 | 311,810 | **940.9 ms** | 1735.2 ms | 1725.2 ms | 1.8x |

三者结果一致（逐组比对）。

### 怎么读这个数字

**别把 1.8x 当成卖点。** 三条路径的主要成本都是"扫日志 + 去重 + 排序"，
状态推导本身只占一小部分，所以倍率上不去。真正的差别在**复杂度形状**：

| | Tier 1 | Tier 2 / `@变量` |
|---|---|---|
| 状态推导 | 编译期完成，运行期零成本 | 每人日一次串行推导 |
| 并行 | 窗口函数可分区并行 | 递归/变量扫描本质串行 |
| 索引 | 谓词已下推，可走 `(uid, in_time)` | 同样可走，但推导仍串行 |
| 物化 | `daily` 可落事实表增量刷新 | 每次全量重算 |
| 规则复杂度上升 | 日程表多几行，运行期几乎不变 | 表达式变长，运行期线性变差 |

最后一行才是关键：r7（补签卡）那种多状态规则，Tier 2 的表达式长度是 r1 的 3 倍多
（`sql_chars` 3252 vs 1068），而 Tier 1 类规则无论多复杂，运行期都只是查一张小表。

## 4. 复现步骤

```bash
# 1) 起一个数据库（二选一）
docker compose up -d mysql8         # MySQL 8.0，端口 3306
docker compose up -d mariadb        # MariaDB 10.11，端口 3307
# 或者用你已有的实例

# 2) 配置连接
export MYSQL_HOST=127.0.0.1 MYSQL_PORT=3306 MYSQL_USER=root MYSQL_PASSWORD=secret
# 或 export MYSQL_SOCKET=/tmp/mysql.sock MYSQL_USER=root

# 3) 跑
make e2e                            # 正确性 + 基准
make e2e-fast                       # 只跑正确性
python3 tests/e2e_verify.py --bench-users 200,1000,4000,10000
```

脚本会自动 `CREATE DATABASE IF NOT EXISTS signin_dsl_test`（可用 `MYSQL_DATABASE` 改名），
并按服务端方言自动下发递归深度与超时上限。

## 5. 基准的已知偏差

- **含客户端进程启动开销**（每次约 10–20 ms），小规模那一行尤其明显。
- **未控制 buffer pool 冷热**；同一规模重复跑波动可 ±15%。
- **单机、无并发**，没有测并发吞吐 —— 而那恰恰是 Tier 1 优势最大的场景。
- **MariaDB 的递归 CTE 实现相当高效**，MySQL 8.0 上 Tier 2 可能更慢，倍率会更大。
  本仓库未在 MySQL 8.0 上实跑过基准，CI 中的 MySQL 8.0 job 只做正确性验证。
- `@变量` 原版在脏数据上会**报错**（见下），基准用的是干净数据。

## 6. 正确性对账中的两个硬证据

行集合完全相同，只改**物理插入顺序**：

```
原始顺序      原版: 错 133/150 组
打乱 seed=42  原版: ERROR 1690 (22003) BIGINT UNSIGNED value is out of range
打乱 seed=99  原版: ERROR 1690 (22003) BIGINT UNSIGNED value is out of range
三种情况下 DSL 产物指纹恒为 bc9dfd41ef，且与参考一致
```

数据与 SQL 一字不改，只切优化器开关：

```
derived_merge=on  → 指纹 496adc8f3e，错 133/150
derived_merge=off → 指纹 90c975ac2f，错 132/150
```

原因：`cast(coin as unsigned)` 的"累计余额"在乱序扫描下不再单调，月末差分下溢；
而派生表 `ORDER BY` 是否生效、同一 SELECT 内用户变量的赋值/读取顺序，MySQL 都不保证。

这两个实验都在 `tests/e2e_verify.py` 里，`make e2e` 会自动跑
（优化器开关实验需要 SUPER 权限，无权限时自动跳过）。

> 注意：**插入顺序实验是稳定复现的**（两种乱序都必然报错）；
> 优化器开关实验的指纹与错组数**随执行计划/统计信息变化**，上面是某一次运行的值 ——
> 这本身就是"结果依赖计划"的证据，但也意味着你复现时数字可能不同。
> 编译产物的指纹在所有情况下恒为 `bc9dfd41ef`。
